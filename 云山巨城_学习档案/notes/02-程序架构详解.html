云山巨城：程序架构与仿作提取笔记

分析对象：C:\Users\YHJ\.codex\attachments\c80f289b-3ff1-429b-be36-156a9470fa95\云山巨城.html。下文行号均指这份原始文件，采用从 1 开始的源码行号。本笔记仅依据静态代码；没有浏览器运行结果，也不把源码中的阈值当作实际性能测量。

1. 核心定位

作品可以理解为一个手工设计的山城空间，经过程序化细化和原生 WebGL2 着色，成为可游览的动态景观。它不是先导入一个现成城市模型再展示，而是在启动时生成地形、道路、建筑、植物、云与灯光数据。

“体素”主要是一套造型和采样语言，不是贯穿全系统的三维体素存储：

  • 自然地形用 1280 × 1280 的二维高度场，每个平面格为 1m；初始自然高度向 1m 量化（340、528–534、603–604）。一个 (x,z) 只有一个地表高度，因此天然不表达洞穴或地形悬挑。
  • 建筑构件统一对齐 0.2m 网格，但通常直接生成一个跨多个体素的长方体表面，而不是保存每个体素占用值（156、160、777–790）。
  • 近看时的 0.2m 表面颗粒、边线、砌石与屋瓦纹路主要来自片元着色器（2814–2833），不需要为每格建立实体几何。
  • 云是少量局部三维占用采样的例外：椭球团合成占用，随后只发出暴露的面（2572–2593）。

这套“较粗几何 + 细颗粒着色 + 人工主构图”的组合，比整座城逐块方砖存储更适合学习本作的视觉机制。

3. 启动数据流

boot()（3383–3422）的顺序具有实际语义：

  1. 初始化 WebGL2 渲染器，编译主材质、阴影、天空、水、点精灵、雾六组程序。
  2. World.generate() 生成自然地形、地表量化、水位、材质和森林倾向。
  3. buildCity(world) 改造高度与占用栅格，同时产生分块的建筑主结构、细节网格、灯晕记录、指定树位和导览段。
  4. world.retainPass() 把人工切削区旁的较高天然边缘改成挡土墙材质。
  5. plantTrees() 在地形及城市留下的空地布树；因此树避让道路/建筑，而不是事后清除。
  6. Scene.makeLOD2() 从改造后的地形生成 2m 远景数据；Renderer.heightTexture() 上传改造后的 1m 地表高度供水与雾使用。
  7. 建立全部远景地形/树网格和水网格，上传城市网格，建立大气和导览，再初始化相机与界面。
  8. 进入动画循环；?test 会禁止正常 requestAnimationFrame，保留手动抓帧入口。

如果仿作时调整地形/城市生成顺序，需重新考虑用地冲突、LOD、挡土墙与高度纹理的同步。当前作品以启动后静态地形为前提，没有自动维护这些派生数据的编辑系统。

4. 世界、地理和城市布局

高度场是城市和自然景物之间的共同接口

World 维护七个等尺寸数组（528–534）：H 为当前地表，nat 为未改造自然地表，W 为水位，M 为材质，occ 为用地占用，mod 为改造掩码，forest 为森林倾向。

这七个数组按声明尺寸共 31,129,600 字节，约 29.69 MiB，仅是静态尺寸计算；尚不包括 wnear、暂存宏观网格、LOD、顶点、索引、GPU 纹理和运行时对象。不能用这个值推断整页实际内存。

保留 nat 与 H 很有价值：道路可以依自然地形采样，建筑可以修改当前地形，材质判定仍可利用自然坡度。占用码是一个简易的空间规划系统（532），不是三维碰撞系统。

主体山势先设计，再加噪声

  • 山脊由折线控制点 [x,z,高度,宽度] 指定（351）；ridgeHeight 计算到各段的距离，沿线插值高度和宽度，用 shapeF 衰减，再用平滑最大值合成（419–439）。
  • ridgeSpire 先扭曲采样坐标，避免山脊过于规则（464–466）。
  • macroFrom 在已设计山势上添加 ridged/fbm 细节，并叠加手工指定的孤峰（458–482）。
  • carveHeight 再切出台地、上下游河道、瀑潭和湖盆（487–521）。
  • 多级采样依次为 4m 山脊/谷底、2m 宏观细化、1m 最终地表（554–604）。这不是递归的体素八叉树。

学习时首先提取控制数据和形状函数；只复制 fbm 会得到随机地形，却丢失这座山城的视觉骨架。

城市是一套带约束的生成语法

buildCity 按云瀑阁、宫城、上城、下城、西山台城、湖岸、山顶、城墙、道路地块填充、空隙补建、街灯、导览的顺序构造（1875–1904）。主要地标与区域都是明确坐标的人工编排，不是随机城市规划器。

City 提供几类可重用操作：

  • plat：改造矩形地表；flight：按 0.2m 高差划分台阶、先切地形再建立踏步；trail：把路径转成轴向折线登山梯（1468、1472、1530）。
  • road：Catmull-Rom 平面路径采样、读取自然高程、平滑/限坡/锚点修正，然后向用地栅格写路面（1582–1644）。
  • lotsAlong：计算道路切线和法线，按加权类型抽取楼房，限制四个朝向，检查用地、水域与挖填高差，再放置（1649–1692）。
  • placeBuilding：根据普通台基或吊脚楼决定是否整平台，采用坐标生成种子，添加门前台阶和灯晕（1694–1724）。
  • archBridge、coveredBridge、wall：分段轴向几何和局部屋顶构件的组合（1738、1785、1822）。

权重配置 LOTS_MARKET / LOTS_RES / LOTS_SLOPE / LOTS_UPPER（1914–1917）是值得保留的风格接口：同一套建筑库通过类型权重、间距、退界、挖填限制、是否吊脚来形成不同片区。

程序化建筑的抽象层

MeshBuilder.box 负责几何，Frame 负责建筑局部坐标，建筑函数负责语义。局部 +z 是建筑正面；只支持 90° 的四种旋转，兼顾网格一致性和简化的轴向法线（797–835）。

Frame 可以同时写入主结构 mb 和细节 md。F.box 是主结构，F.d 或 detail 参数把栏杆、翘角等写进细节网格。细节不只是代码分类，它直接连接 360m 绘制距离和 200m 阴影距离（3366）。

roof() 最有学习价值（980–1057）：以 0.2m 垂直层堆叠，横向收缩使用 t^0.62 而非线性斜坡；gable 为双坡，hip/pyr 同时缩 x/z，xs 让 x 收缩在一定处停止以呈现歇山特征。再分别叠加檐板、屋脊/宝顶、鸱吻和逐级檐角上扬。无需导入曲面屋顶模型，便能保留中式轮廓的几个识别点。

仿作时应保留“台基 → 柱/墙 → 檐 → 屋顶 → 屋脊 → 门窗灯火”的组合层级，让比例、屋顶参数和材质有明确配置，而不是复制散落盒子坐标。

5. 网格、材质和渲染机制

压缩顶点与几何批次

顶点格式为 20 字节：position 3 个 float32，color RGB + AO 4 个 byte，normalIndex + glow + flags + random 4 个 byte（719、742–750）。法线只保存 0–5 六个轴向编号，在 GLSL 展开（2799）。四边形用 4 顶点、6 索引；AO 不对称时选择不同三角剖分，减弱阴影插值对角痕迹（756–762）。

这比通用 position/normal/uv/material-id 顶点更紧凑，但它依赖纯轴向面。若需要自由旋转建筑、斜面或有机曲面，应更换顶点法线方案，而不能只增加 rot 的取值。

地形只生成顶面和比邻格更高的暴露侧面；同高、同材质、同色且无需 AO 变化的一行顶面可以合并（894–939）。这是单方向条带合并，不是完整二维贪心网格。分块边缘加 3m 裙边遮蔽不同 LOD 接缝（929–930）。水面也沿行合并相同水位连续段（942–955）。

建筑网格按“中心点所在块”分配主结构和细节批次（1452–1461）。一个跨块的建筑仍完整留在一个批次里；不会沿块边界裁开。几何包围盒仍记录实际范围，可供视锥判断，但细节距离依据所属块，不是逐构件距离。

FL 的 8 个位（720）相当于材质行为标签；同一个主 shader 根据标签组合行为。这是紧凑的效果系统，但 byte 全部用满，扩展类别前应规划更宽字段或新的材质映射。

光照不是 PBR：主光采用法线点积，环境光在地面色和天空色之间按法线 y 分量插值，顶点 AO 只调制环境项；无 roughness/metallic 或 BRDF 材质（2849–2858）。屋瓦看起来有明暗层次，并不意味着存在真实瓦片法线贴图。

多阶段绘制

Renderer.render（3134–3285）的顺序：

主光阴影 → 全屏天空 → 不透明地形/建筑/树/远山 → 透明水 → 加色倒影灯晕 → 半透明体素云 → 两层云海 → 瀑布水雾点精灵 → 加色灯晕。

阴影是单张跟随相机焦点的正交深度贴图，默认 4096²，硬件最大纹理尺寸较小时使用 2048²（3032–3034）。光源相机的中心对齐到阴影 texel，减少移动时抖动；表面法线偏移、固定深度 bias、polygon offset 和四次比较采样共同缓解阴影痤疮（2800–2807、3147–3172）。它不是级联阴影，范围变大时阴影分辨率会被摊薄。

各对象包围盒经视锥剔除（3114–3131、3200）。stats.drawn/tris 只统计不透明主 pass 的绘制和三角形（3198–3204、3284），不能当作全部 pass 总绘制量。

水、云、雾的视觉近似

  • 水面高度不做物理模拟。高度纹理提供水深；两层噪声有限差分生成波面法线，Fresnel 混合浅绿/深青水色和程序化天空，叠加太阳高光与浅水泡沫（2929–2954）。
  • 水中反射的天空是真正使用 reflect 计算的程序化环境色，但建筑/山体不进入反射贴图。水中灯光来自附近灯晕按水位分组、镜像 y 的点精灵（2533–2547、2971、3231–3234），不是完整场景平面反射。
  • 体素云预生成静态网格，以 uniform 位移水平漂浮与轻微上下运动；按云中心距离从远到近排序，靠近相机时降低透明度（2606–2618）。
  • 云海只有 y=46m、148m 两层大平面；噪声、距地高度、距相机距离、清晰区域椭圆掩码决定 alpha（2600–2602、3005–3018）。它不是三维体积散射。
  • 常规空气透视使用高度衰减雾的沿视线积分，再叠加距离 haze，并让面向太阳的雾偏暖（2770–2779）。这是空间层次的主力效果。
  • finish 在各材质片元中分别做 ACES 近似、1.14 饱和度和 gamma 输出（2781）；没有独立 HDR 后处理链、真实 bloom 或景深 pass。灯火的柔晕由加色点精灵直接提供。

6. 时间、相机和交互

两个时钟

App.hours 是一天内的时刻，用来控制日月、光照、天空、雾、灯火；App.clock 是持续动画时间，用来控制水、瀑布、云、星星和灯火闪烁（3375–3379、3718–3719）。暂停时间只停止 hours，clock 仍然前进。因此可以冻结落日的光照，同时水与云继续运动。

computeEnv(hours, clock) 用固定纬度 30° 和固定太阳赤纬 12° 算太阳方向，再按太阳高度插值设计好的天空色关键帧；根据太阳/月亮强度选择唯一主光，计算清晨/傍晚雾、夜间曝光和亮窗比例（2663–2748）。这些参数构成艺术性日夜系统，不是日期/地点精确天文模拟。

一天在 ×1 下由 DAY_SECONDS=480 指定为约 8 分钟（3379）。这是代码参数，不是观察得到的运行数据。

相机不是自由飞行控制器

自由模式其实是围绕目标点的 orbit 相机（3458–3468）：yaw、pitch、dist 决定位置，拖动旋转、右键/Shift 平移、滚轮指数缩放，WASD 移动目标，QE 调目标高度（3636–3655、3723–3731）。相机位置至少在高度场/水位之上 1.5m，但没有建筑碰撞。

8 个预设景点保存在 VIEWS（3439–3448）。flyTo 做最短角度变化，三次缓入缓出，距离采用对数插值并增加跨场景升高（3474–3488）。这是观看节奏的一部分，仿作时可把它保留为“镜头配置”，而不要和城市硬编码混合。

双击聚焦通过反投影产生射线，然后每 1.5m 前进一次寻找高度场命中（3685–3698）。它只选地面/水面，不选建筑表面；这是近似射线采样，精度与步长相关。

导览不是导航网格寻路。它由作者指定的道路、台阶与山径拼接并以约 1m 重采样（2359–2382），再做 11 点平滑与弧长索引（3492–3502）。相机以约 4.2m/s × 倍速沿路径前进，朝前方 14m 看，同时在若干区段把视线引向地标；拖动产生临时偏移，2.5 秒后自动衰减归位（3535–3564）。

这一“路径 + 地标注意力区间”结构非常适合仿作：它将空间展示变成叙事。需要注意导览路径与建筑布局目前靠人工同步，路径平滑后没有逐帧碰撞修正。

7. 性能策略与维护限制

已明确实现的优化：

  • 多级地形采样，减少昂贵的山脊距离运算次数（554–579）。
  • 64m 网格分块，共 20 × 20 块；全部远景先生成，近景按需生成（3290、3297）。
  • 近景 1m 地形/详细树，远景 2m 地形/简化树；250m 进入、330m 释放的滞回避免边界抖动（3291、3331–3357）。
  • 常规每帧最多建立 2 块近景（3736）；主结构保留，建筑细节随距离剔除。
  • 视锥剔除、顶面条带合并、水面行合并、短索引自动选择、顶点压缩（894、942、3086–3089、3114）。
  • 90 帧平均间隔超过 38ms 就逐级降低 DPR 上限，低于 18ms 才逐级恢复，上限序列 1.5/1.25/1.0/0.8/0.66（3742–3749）。这是反馈规则，不证明任何设备上的帧率。

仿作前值得处理的限制：

  1. 启动主线程阻塞。 boot 是 async，但 world.generate、buildCity、plantTrees 均同步；只是阶段之间和每 50 个远景块之间让出事件循环（3381、3393、3396、3401、3407）。扩城后可把纯数据生成移到 Worker，或按时间预算分批执行。
  2. 几何是烘焙结果。 上传完成即 city.builders=null（3435）；没有按建筑 id 保留对象/编辑接口。地形运行时变更也不会自动更新高度纹理、LOD 和网格。若做编辑器，需设计增量失效与重建。
  3. 世界尺寸多处硬编码。 CPU 使用 WN/WH，而水和雾 GLSL 写死 640/1279（2929、3005）；雾清晰区、各城坐标、镜头、导览注意力也写死。单改 WN 不足以扩展世界。
  4. 坐标数组约定混用。 道路点为 [x,z,y]（1623），导览为 [x,y,z]（2363、2367）。应显式类型化或统一记录字段，减少拼接错误。
  5. 可复现但有顺序耦合。 城市主 RNG 固定种子（1443），建筑的局部 RNG 常由位置产生（1703），植物/云也固定种子。新增前置随机抽样会改变后续布局；按区域/地块派生独立 seed 能缩小这种变化。
  6. 几何假设强。 Frame 只支持四向，法线只支持轴向，盒子内面除手工 skip 外并不做全局剔除。自由旋转、斜向道路建模或大量重复建筑应重新考虑普通法线、实例化或几何合并。
  7. 透明排序有限。 只有云按中心距离排序，云的内部面、水块、两层雾固定顺序；复杂交叠或进入云层后可能出现透明近似。需用实际画面验证，而不是静态判断一定发生。
  8. 灯反射没有水域裁剪。 灯晕根据附近存在水位而加入镜像组，绘制点精灵不使用水域掩码（2533–2547、3231–3234），所以岸边复杂构图值得检查。
  9. GPU 生命周期不完整。 有 mesh free（3091），但没有上下文丢失/恢复、完整程序/纹理/点精灵释放、阴影 FBO 完整性检测；单次页面使用通常不受重建影响，做组件反复挂载时需补充。
  10. 源码注释有少量漂移。 H 注释称 0.2m 精度（528），初始自然地形实际 1m 量化、改造才可用 0.2m（603–604、1468）；远山注释称 16m（2622），实际平面步长 12m、高度量化 4m（2634、2641）。阅读时应以代码为准。
  11. 减弱动态偏好只影响 CSS。 prefers-reduced-motion 只关掉载入/提示的 CSS transition（98），不会暂停云、水和导览。做公共可访问版本可以接入动画系统。

8. 学习和仿作的提取顺序

建议分三次提取，而不是先大改整座城市：

第一阶段：单体构件实验。 提取 RNG、snap、调色板、MeshBuilder、Frame、roof 和一种建筑；只做一个台基/殿/亭，调整檐宽、起翘、屋顶坡度和层高。产物应是可配置组件，输入尺寸/朝向/配色，输出主结构和细节网格。能解释每个轮廓由哪一层产生后，再扩展民居与高楼。

第二阶段：小场景验证完整风格。 做约 128m 或 256m 的小地图，先手工放山脊、台地、河流和一个主地标，再用道路/地块规则补若干建筑和树。保留主材质 shader、雾、天空和夜灯；先不追求整城密度，因为空气透视与色调联动才是本作规模感的重要来源。

第三阶段：可复用生成架构。 将源码的伪模块拆成真正模块，并把地理控制点、城域布局、片区地块规则、镜头和导览注意力变为配置数据。待重复小场景稳定后，再引入分块 LOD、Worker 和质量自适应。

可以采用以下设计接口；它们是仿作建议，不是原文件现有 API：

type WorldSpec = {
  sizeMeters: number; cellMeters: number; voxelMeters: number; seed: number;
  ridges: RidgeSpec[]; rivers: RiverSpec[]; plateaus: PlateauSpec[]; lakes: LakeSpec[];
};
type DistrictSpec = {
  roads: RoadSpec[]; lotRules: LotRule[]; landmarks: BuildingPlacement[];
};
type BuildingSpec = {
  kind: string; width: number; depth: number; floors: number;
  roof: { kind: string; pitch: number; lift: number; palette: string };
  seed: number;
};
type EnvironmentState = {
  hours: number; animationSeconds: number;
  // 太阳、天空、雾、灯火等由统一环境模型计算。
};
type TourSpec = {
  path: Vec3[]; stations: Station[]; attention: AttentionInterval[];
};

generateTerrain(spec: WorldSpec): WorldData;
planCity(world: WorldData, districts: DistrictSpec[]): CityPlan;
buildArchitecture(frame: Frame, spec: BuildingSpec): GeometryPair;
computeEnvironment(state: EnvironmentState): EnvironmentUniforms;
updateTour(tour: TourSpec, progressMeters: number, dt: number): CameraState;

CityPlan 最好先保存建筑 id、地块、局部 frame 和配置，再由 buildArchitecture 转几何；原文件现在把规划和几何发射放在一起。这样更容易学习、保存、调参、导出和重新生成。

如果仿作题材换成另一个山镇，应换掉山脊/水系/地标布局和屋顶比例等显著设计，保留“主构图先行、规则补密度、细部按距离淡出、统一环境驱动”的机制。机械复用整城坐标只会得到原图的变体，无法真正验证对构图与架构的理解。
