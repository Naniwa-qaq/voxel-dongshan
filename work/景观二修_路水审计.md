# 2026-10-22 · 二修的路水审计与实现

本轮修改的是从源资料到画面的综合表达。原 `design.json`、`design.js`、OSM 快照和生成器均保持只读。结果在 `东山镇_重制版/js/landscape-revision.js` 中作为显式补丁载入，执行顺序为 `design.js → landscape-revision.js → scene.js`。新增的镇区/设施独立模块不受这个补丁影响。

## 1. 截图中的断头河是什么

当前样区有三条完整通湖线和一条南边界残段。三条完整线的村内端就终止在原始 `water.json` way 的第一个节点；不是简化后丢点，也不是当前样区边界切断。原始节点数与几何坐标数分别为 12/12、6/6、7/7，没有几何缺点。

| OSM 源线 | 村内端原始节点 | 最近另一条已记录水道 | 最近已记录水面 |
|---|---:|---:|---:|
| `way/1104698619` | 10108911170 | 138.27 m | 221.43 m |
| `way/1104698622` | 10108911184 | 122.31 m | 226.80 m |
| `way/1104698625` | 10108911192 | 138.95 m | 271.65 m |

距离在 EPSG:32651 中计算。三个端节点均未与本地原始水道的其他 way 共享；没有近处可靠塘面可供接合。这里能够确认的是「源记录到此结束」，不能据此确定实际沟港也在此终止，更不能把相隔百余米的水系凭空连起来。当前资料也没有支持新增上游塘面、暗涵或水工闸口的证据。

原版把三个未解决端点都画成 **4.6 m 等宽、亮色石岸、平水面渠道**。一个资料边界因此被渲染成硬质人工端墙，断头感被放大。这是表达失败，不应通过补画假河来掩盖。

二修保留三个源中心线、源端点与通湖关系，改成 2.2–2.6 m 的类型化窄沟；原线最靠近村内端的 14–20 m 在原线内部渐窄到 0.8 m，以低岸草、土沟和少量旧石收口。终点附近不新增水面，不延长中心线，不加入假塘或假暗涵。显示宽度是制图表达，资料并没有提供这些实测河宽。

第四条 `way/1104698628` 的河首位于样区外，当前只留下南边界附近约 13 m 的碎段。本轮整体择除这个图边残段；原源线完整保留在资料中。

## 2. 截图中的湖岸白圈是什么

湖岸附近的白色闭环不是建筑基础，也不是新增园林。它们是 OSM 的 `highway=service` 附属道路回环。标签没有名称或公共设施功能说明；旧渲染器把所有道路都铺成很亮的连续石色，因此附属车道被读成了空地上的基座轮廓。

明确择除以下低等级显示线段：

- `way/1094233028:1`：湖岸附属回环；保留同源 `:0` 接近段，改窄土路。
- `way/1098577064:1`：附属回环；保留同源 `:0` 接近段，改窄土路。
- `way/1094233030:0`：南边界附属回环的裁切残段。

同时择除 `lane-LX-023` 与 `lane-LX-110`。它们是原版人工设计步巷，路尾仅接入本轮择除的回环；保留会出现悬空路尾。没有为它们捏造新的 OSM 道路。其余人工步巷仍明确保持「综合设计」属性。

保留的 11 段 primary / residential / unclassified 源道路，其 ID 和中心线全部不变，主路通达没有被删除。既有建筑选择仍沿用原来更保守的街坊约束，没有跨水跨路重新归并。

## 3. 路面分级

| 类型 | 新显示宽度 | 材质语义 | 边缘与铺缝 |
|---|---:|---|---|
| 主路 primary | 6.8 m | 旧沥青/灰色路面 `aged-grey-road` | 连续；无装饰性石缝 |
| 住宅路 residential | 3.0 m | 旧石混铺 `mixed-old-stone` | 软破边；可用少量石缝 |
| 普通道路 unclassified | 3.8 m | 灰土路 `grey-earth-track` | 软破边 |
| 附属道路 service | 1.6 m | 夯土 `packed-earth` | 柔和边缘；无统一白石基座 |
| 山径 path | 1.0 m | 林地土路 `woodland-earth` | 柔和边缘 |
| 步道 footway | 1.2 m | 风化旧石 `weathered-stone` | 破边；少量铺缝 |
| 设计步巷 lane | 1.0 m | 土石混铺 `packed-earth-stone` | 柔和边缘 |

所有宽度都是本图的制图显示尺寸。主路、普通路和步巷不能再由一个统一浅色值决定外观。桥面宽度同步随其承载道路调整。

## 4. 给渲染器的接口

`DSDesign.water.canals` 的每条保留沟港新增：

```js
{
  width: 2.4, // 主体显示宽度，各线略有差别
  head: {
    pointIndex: 0,
    taperLength: 18,
    widthAtHead: 0.8,
    endTreatment: 'vegetated-drain-head',
    evidence: 'unresolved-source-end'
  },
  widthProfile: [
    { distanceFromHead: 0, width: 0.8 },
    { distanceFromHead: 18, width: 2.4 }
  ],
  bankStyle: 'low-earth-stone-mix',
  bankBuffer: 0.8
}
```

宽度按中心线上从第一个点开始的累计距离线性插值，超过 `taperLength` 使用 `width`。不要仅缩窄水面而保留原 4.6 m 的硬质槽岸；地形挖槽、岸材质和植被避让应共同使用新宽度。

`DSDesign.water.terminals` 为三个低岸草沟端提供 `x`、`z`、`sourceId`、`directionFromHead`、`taperLength`、`widthAtHead`、`grassRadius`。方向指向既有中心线内部。`pond:false`、`culvert:false`、`stoneCap:false` 明确禁止擅加塘面、涵洞和封口石墙。

道路新增 `surface`、`edgeStyle`、`renderPriority`、`pavingJoints` 与 `roadsideCurb:false`。根节点 `DSDesign.landscapeRevision` 留下版本和拓扑处理原则。

## 5. 再生和检查

运行 `scripts/revise_landscape.py`，使用已安装的 GDAL Python。它不访问网络，不使用 ArcPy，不导入会重写基线的原设计生成器。

产出：

- `东山镇_重制版/js/landscape-revision.js`：浏览器补丁。
- `东山镇_重制版/data/landscape-revision-audit.json`：每项源 ID、旧/新状态、理由、端点证据、源 SHA256 和补丁完整副本。

脚本内独立断言检查：11 段重要源道路 ID 保持一致；3 条保留沟港中心线完全一致；新增水道和新增塘面均为 0；源资料与基线文件 SHA256 不变。当前道路显示线段由 90 段减到 85 段，沟港由 4 条减到 3 条。渲染层的草地大色块、逐屋浅色定位垫和整院染色由主任务另行修正，本补丁不修改 `scene.js` 或 `architecture.js`。
